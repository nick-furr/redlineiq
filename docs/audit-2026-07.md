### Convergence

Both lanes return the identical `{ pages, allMarkups, totalMarkups, stats }` shape
(contract stated at `parse-extraction-service.js:9-11`, `tiled-extraction-service.js:101-106`).
The single convergence point is `addExtractionResults()` at `src/services/project-service.js:165`,
which flattens `pages[].markups[]` into `checklist_items` rows — the whole markup object is
stored as JSON (`project-service.js:181`), with `page_number` merged in from the page wrapper
(`project-service.js:172`). Everything downstream (SSE job events, `src/routes/api.js`, FTS
triggers in `src/services/db.js:66-78`, React client) is lane-agnostic.

### Routing

Automatic, no manual override anywhere. `probeAnnotations` counts annotations whose subtype
is in the `MARKUP_SUBTYPES` whitelist (`pdf-annotation-probe.js:18-21`; Link/Popup/Widget
deliberately excluded) across **the whole document**, then:
`markupCount > 0 → 'digital_annotation' → parse`, else `→ 'raster' → vision`
(`pdf-annotation-probe.js:45`, `:59-61`). This is Phase 1 of the hybrid design; the
`digital_flattened` regime (color-filtered content-stream parse) is explicitly deferred to
Phase 2 (`docs/superpowers/specs/2026-06-02-parse-vision-hybrid-extraction-design.md:131-134`).

### Mixed PDF — actual behavior

**Routing is document-level, so a mixed PDF loses its raster pages silently.** Traced:

1. One live annotation anywhere in the file → `markupCount > 0` → the *entire* document
   routes to parse (`pdf-annotation-probe.js:45`).
2. On the parse lane, a flattened/scanned page simply has no qualifying annotations, so
   `parseAnnotationLayer` pushes a page with an empty `markups` array
   (`parse-extraction-service.js:53`) — no error, no warning, no vision fallback.
   `labelMarkups` skips the API call for empty pages (`:98`). The page counts as
   "processed" in stats (`:137`).
3. The inverse also holds: a scanned set with one stray live annotation (e.g. a leftover
   sticky note) mis-routes the whole set to parse and extracts almost nothing.

The probe already computes `perPageCounts` (`pdf-annotation-probe.js:31-47`) but **no caller
consumes it** — it is asserted in `test/test-annotation-probe.js:23` and otherwise dead. The
design spec names this exact risk ("`>0` whole-file routing… Per-page routing is the deferred
mitigation", spec `:148-150`). Per-page routing is therefore a data-shape-ready but unbuilt
mitigation.

One more routing divergence: **the CLI's raster path is not the production raster path.**
`src/scripts/extract-cli.js` routes identically (`:106-110`) but its vision branch uses
un-tiled `pdfToImages` + `extractAllPages` (`:24-27`, `:119-129`), while production tiles
every raster page (`job-service.js:128-134`). README (`README.md:43`) and CLAUDE.md say the
CLI "applies the same source-type routing" — true for routing, misleading for extraction.

## 2. Parser Output Shape

### Fields per markup (parse lane)

Built at `parse-extraction-service.js:44-50`, enriched at `:82-94` (`applyLabels`):

| Field | Source | Survives to final output? |
|---|---|---|
| `id` | generated, renumbered globally in `assembleResult` (`:118-128`) | yes |
| `markup_text` | `a.contentsObj.str \|\| a.contents` (`:41`) | yes |
| `markup_type` | text-only LLM label, fallback `note` (`:88`) | yes |
| `related_to` | LLM label, remapped after renumber (`:127`) | yes |
| `confidence` | LLM label, fallback `high` (`:90`) | yes |
| `ambiguous` | LLM label (`:91`) | yes |
| `drawing_reference` | **hardcoded `'Unknown'`** (`:46`, page-level `:53`) | yes (as 'Unknown') |
| `location_on_drawing` | **always `''`** (`:47`) | yes (empty) |
| `coordinates` | `{ page, rect: Array.from(a.rect), subtype }` (`:49`) | **yes — confirmed** |

**/Rect and page index survive end to end.** `applyLabels` spreads the original object
(`:85-92`), `assembleResult` mutates in place without stripping fields, and
`addExtractionResults` serializes the whole markup to the `markup` JSON column plus a
top-level `page_number` (`project-service.js:172,181`). The data model documents this
contract (`src/models/markup.js:61-64`: PDF points, bottom-left origin, parse-path only,
absent on vision markups). Verified by `test/test-parse-extraction.js:30-31` (4-tuple rect,
`coordinates.page` set) against a real eval PDF.

Two shape caveats:

- **Text-less annotations are dropped entirely** (`parse-extraction-service.js:42`). A cloud
  or circle with no `/Contents` never reaches the output — on case_012 the probe sees 24
  annotations (`test/test-annotation-probe.js:22`) but the parser keeps 12. This makes the
  eval convention's seeded "commentless ambiguous cloud" (`case_012` label `m12`,
  `evals/labels/case_012_sanmarcos_s201_framing.json:22`) structurally uncatchable on the
  parse lane — a built-in recall ceiling, not a model failure.
- The pdfjs annotation `id` (object ref) is **not** captured — relevant to write-back, §5.

### Subtypes handled

Whitelist at `pdf-annotation-probe.js:18-21`, shared by probe and parser
(`parse-extraction-service.js:19,38`):
`FreeText, Square, Circle, Polygon, PolyLine, Line, Ink, Highlight, StrikeOut, Underline,
Squiggly, Text, Stamp`.

Ignored/unhandled: `Popup`, `Link`, `Widget` (deliberate — structural chrome), plus `Caret`,
`FileAttachment`, `Redact`, `Sound`, `Movie` (simply not in the set). Within the handled set,
any instance without text is dropped per the caveat above regardless of subtype.

### Bluebeam-specific data

**None of it is read.** No references to `BSISettings`, `BSIColumnData`, custom columns,
status models, or `/IRT` anywhere in `src/` (grep confirms zero hits). Consequences and
hook-in points:

- **/IRT reply trees:** replies (Text annotations carrying `inReplyTo`) pass the subtype
  whitelist and are emitted as *independent* markups — a Bluebeam status reply or comment
  thread would show up as duplicate checklist items rather than metadata on the parent.
  pdfjs exposes `inReplyTo` / `replyType` on the annotation objects, so the natural hook is
  the annotation loop at `parse-extraction-service.js:37-52` (filter replies out, or fold
  them into the parent's fields before labeling).
- **Custom columns / BSISettings:** these live in document-level structures that
  `page.getAnnotations()` does not surface. Reading them requires a raw object walk
  (pdf-lib's low-level API or hand parsing) — a new utility next to
  `pdf-annotation-probe.js`, not an edit to the existing loop.

## 3. Eval Harness State

### Case coverage vs the parse lane

Label inventory: **16 label files** — 12 working-set (`case_001`–`case_012`) + 4 holdout
(`case_h02`–`case_h05`). `evals/pdfs/` holds 14 PDFs: the 12 labeled cases plus
`case_011_*_flattened.pdf` and `case_012_*_flattened.pdf`, which have **no labels** and are
skipped with a console warning (`evals/run-eval.js:95-99`).

Only **two cases exercise the structured-annotation lane**: case_011 and case_012 are the
only labels with `"source_type": "digital_annotation"` (grep over `evals/labels/`). Everything
else is raster (mostly synthetic; case_006/007 are the real photographed/mixed cases). The
`digital_flattened` regime has zero labeled coverage — its fixtures exist but are unlabeled,
and per the design spec they carry PDF-XChange "DEMO" watermarks that need a clean re-flatten
before they can be scoring fixtures (spec `:151-154`).

### Can `npm run eval` hit the parse lane today?

**Yes.** The harness routes each case through the production router by default
(`run-eval.js:105-118`): case_011/012 probe as `digital_annotation` and run through
`extractAllPagesParsed` (`:116-118`). Per-regime breakdown and router accuracy are reported
via `evals/lib/regime-summary.js`. `--force-vision` keeps the parse-vs-vision delta measurable
(`run-eval.js:45`).

Two integrity caveats:

1. **The default vision path in the harness is NOT production's vision path.** Without
   `--tile`, raster cases run single-image `extractMarkupsFromPage`
   (`run-eval.js:131-137`), while production always tiles (`job-service.js:128-134`). The
   header comment "the harness measures the real production system" (`run-eval.js:42-44`)
   is only true for routing. Comparing a default run against production behavior conflates
   two configurations.
2. **Parse-lane eval numbers are currently non-deterministic** — see §4: `labelMarkups`
   omits `temperature`, so the parse lane's semantic labels run at API default 1.0,
   violating ADR 0003 on the exact lane the next phase depends on.

Extending coverage requires: label the two `*_flattened` fixtures (after clean flatten),
and add more `digital_annotation` cases — the harness itself needs no code changes for
either (labels resolve by filename, `evals/CONVENTIONS.md:3`).

### Ground truth location and schema

`evals/labels/<case_id>.json`, one per PDF in `evals/pdfs/` (holdout PDFs in
`evals/holdout/`, excluded by `--working-set`). Schema (see
`evals/labels/case_011_walpole_c401_grading.json`):

```json
{
  "case_id", "source_type", "discipline", "sheet",
  "substrate_source", "markup_source", "markup_modality",
  "page_count", "notes",
  "expected_markups": [
    { "id", "concept", "category", "page", "specificity_target": 0|1|2, "is_ambiguous" }
  ]
}
```

Matching is LLM-judge conceptual equivalence (Haiku, temp 0, `evals/lib/llm-judge.js`);
scoring in `evals/lib/score.js`. Note the judge sees only `markup_type`, `markup_text`,
`location_on_drawing` (`llm-judge.js:27`) — coordinates play no role in scoring. Taxonomy and
the rule that headline metrics should cover `annotation`-modality only live in
`evals/CONVENTIONS.md:54` (case_007 is labeled but mixed-modality; the harness does not
currently enforce that exclusion — it scores whatever has a label).

- `inspect-pdf.js` (root) — self-declared "THROWAWAY DIAGNOSTIC" (`:2`), imports pdfjs from

  `MARKUP_SUBTYPES` (`:25-28`).
- `probeAnnotations().perPageCounts` — computed (`pdf-annotation-probe.js:31-47`), consumed
  by nothing but a test assertion. (Keep it — it is the input per-page routing needs — but
  today it is dead weight.)
- Committed artifacts: `.playwright-mcp/*.yml` page snapshots,
  `evals/synthetic/_lib/__pycache__/`.

### Duplicated logic between lanes

- **Global ID renumbering + `related_to` remap exists four times:**
  `extraction-service.js:197-209`, `tiled-extraction-service.js:131-139`,
  `parse-extraction-service.js:118-128`, and as the reusable

  `extraction-service.js:239-254`, `tiled-extraction-service.js:158-172`,

### Hardcoded values / hacks that will bite (file:line)

- **`parse-extraction-service.js:99-104` — `labelMarkups` sets no `temperature`.** The only
  Claude call site in the codebase without it (every other site pins 0:
  `extraction-service.js:79`, `ask-service.js:134`, `evals/lib/llm-judge.js:35`). Violates
  ADR 0003's explicit rule 4 ("always set temperature in every new API call site") and makes
  the shipped parse lane — and its eval numbers — non-deterministic. One-line fix, highest
  priority in this report.
- `extraction-service.js:150-155` — 429 handler comments "retry once" but recurses with no
  attempt counter: unbounded retry under sustained rate limiting.
- `parse-extraction-service.js:46,53` — `drawing_reference` hardcoded `'Unknown'`. The design
  spec's field table promised "title-block as today" (spec `:100`). Degrades `/ask` FTS
  retrieval (sheet refs are indexed, `db.js:56-64`) and any per-sheet grouping for parse
  projects — and is the main gap for coordinate linking (§5).
- `src/scripts/extract-cli.js:112-115` — `--pages` silently ignored on the parse path.
- Stale "eval-only" headers: `tiled-extraction-service.js:2,13-14` ("eval prototype…
  Production extraction is unchanged") and `pdf-tiler.js:2,10-12` ("Tiling is eval-only until
  the hypothesis is validated") — both are the production raster path since Phase 1 shipped
  (`job-service.js:128-134`). Actively misleads a reader doing exactly this audit.
- `pdf-tiler.js:22` — `1568` is coupled to Sonnet 4.6's server-side resize cap; a model bump
  silently invalidates the tiling geometry. Same class: `RASTER_DPI=200` (`:24`),
  `MIN_LONG_EDGE_IN_FOR_TILING=12` (`:25`), `TILE_CONCURRENCY=4`
  (`tiled-extraction-service.js:42`), pdf-converter's `width: 2400 / height: 3200`
  (`pdf-converter.js:60-61`).
- `evals/lib/llm-judge.js:10` — judge model hardcoded (fine, but it bypasses the
  `CLAUDE_MODEL` env convention; worth a comment at minimum).

### Dependencies

All 14 root dependencies are imported somewhere (verified by import tally across
`src/`, `evals/`, `scripts/`, `test/`). Client deps are all standard Vite/React/Tailwind.
Flags:

- `@anthropic-ai/sdk ^0.39.0` (`package.json:18`) — notably old by mid-2026, and no
  documented reason: ADR 0003 pins *model IDs and temperatures*, not the SDK version. Either
  document the pin or schedule a bump (checking `contentsObj` fallback behavior in
  `parse-extraction-service.js:40-41`, which was written to survive exactly this kind of bump).
- `pdf-lib ^1.17.1` — unmaintained upstream (last release 2021). Currently used only for page
  counts/geometry (`pdf-converter.js:195-201`, `pdf-tiler.js:57-65`, scripts), where it's
  fine — but it is the load-bearing assumption in the write-back feasibility (§5).
- `pdfjs-dist` is intentionally the `legacy` build for Node (`pdf-annotation-probe.js:14`) —
  documented by usage, no issue.

## 5. Feasibility Notes

### Coordinate linking (per-sheet AutoLISP zoom to /Rect) — **small addition**

Already there:
- `coordinates: { page, rect, subtype }` in PDF points, bottom-left origin, per parse-lane
  markup — persisted into the `markup` JSON column and queryable
  (`parse-extraction-service.js:49`, `project-service.js:181`, contract at
  `models/markup.js:61-64`).
- `page_number` per checklist item (`project-service.js:172`).

Missing:
1. **Sheet identity.** `drawing_reference` is `'Unknown'` on the parse lane
   (`parse-extraction-service.js:46`), so "per-sheet" grouping today means "per page
   number" plus a user-supplied page→DWG/layout mapping. Populating drawing_reference
   (title-block read, or letting the existing label call infer it from markup text) is the
   one upstream fix worth doing first.
2. **Coordinate transform.** `/Rect` is paper-space PDF points; AutoLISP paper-space zoom
   (`ZOOM Window` in a named layout) wants layout units. If sheets are plotted 1:1, the
   transform is `pt / 72` inches — trivial — but plot scale/offset is an assumption per firm
   that needs verifying, not code.
3. **The generator itself.** A new script (roughly the size of
   `scripts/generate-blank-plan.mjs`) that queries a project's items, groups by page/sheet,
   and emits one `.lsp` per sheet, plus a CLI flag or export route to trigger it.

Nothing structural: the result shape, persistence, and API all already carry the data.
Vision-lane markups have no coordinates (`models/markup.js:64`) — this is a parse-lane-only
feature until tile-position back-projection is built, which *would* be structural.

### Status write-back (write a reply annotation into the source PDF) — **structural change**

Nothing in the stack touches annotation writing today. pdf-lib usage is read-only page
geometry (`pdf-converter.js:195-201`, `pdf-tiler.js:57-65`) and page copying/drawing in
one-off scripts (`scripts/extract-source-page.mjs`, `scripts/generate-blank-plan.mjs`).

What writing a status reply (Bluebeam-style: a `Text` annotation with `/IRT` → parent and
`/State`/`/StateModel`) would require:

1. **A durable source PDF.** `uploads/` is ephemeral on Render (`README.md:184`) — by the
   time a drafter marks an item done, the original PDF may be gone. Write-back forces the
   object-storage move the README already flags. This is the actual structural part.
2. **A handle back to the source annotation.** The parser does not capture the pdfjs
   annotation `id` (object ref) — only `rect`/`subtype`
   (`parse-extraction-service.js:49`). Matching by rect is fragile; capturing `a.id` at
   parse time is a one-line forward-compatible addition worth making *now*, before more
   projects accumulate.
3. **Low-level PDF writing.** pdf-lib 1.17 has no high-level annotation API — this means
   constructing raw `PDFDict`s (`/Type /Annot /Subtype /Text /IRT ... `) and appending to
   the page's `/Annots` array via `pdfDoc.context`. Contained (~one utility module) but
   genuinely low-level, on an unmaintained library; evaluating a maintained alternative or
   an incremental-update writer belongs in the spike.

Estimate: coordinate linking = **small addition** (1 upstream field fix + 1 generator
script). Status write-back = **structural** (durable storage prerequisite + annotation ref
capture + low-level writer or new dependency).

## State of the codebase

RedlineIQ is in genuinely good shape for a parked solo project: the hybrid architecture that
the docs describe is the architecture the code implements, both lanes converge on one
verified result shape, the parse lane's `/Rect` + page coordinates survive intact into
SQLite, and the eval harness really does route and score the production parse path with
regime breakdowns and router accuracy. The documentation is unusually honest and the tests
cover the pure logic offline. The soft spots are all at the seams the next phase will lean
on: document-level routing silently discards raster pages in mixed PDFs (the per-page data
to fix it is already computed and thrown away), the parse lane's one LLM call is the only
unpinned-temperature call site in the repo — quietly violating the project's own
determinism ADR on the exact lane that's now primary — the eval's default vision
configuration no longer matches production's tiled path, `drawing_reference` is a hardcoded
`'Unknown'` on parse output, and a layer of stale "eval-only" comments and dead files
misdescribes what shipped.

**Highest-leverage cleanups, ranked:**

1. **Pin `temperature: 0` in `labelMarkups`** (`parse-extraction-service.js:99`) — one line;
   restores ADR 0003 compliance and makes parse-lane eval numbers trustworthy before any
   Phase 2 measurement.
2. **Fix the stale-truth layer**: rewrite the "eval-only/prototype" headers in
   `tiled-extraction-service.js` and `pdf-tiler.js`, and either tile the CLI's raster path or
   correct the "CLI applies the same routing" claims in README/CLAUDE.md — anyone (including
   agents) reading these today gets the wrong architecture.
3. **Delete the dead weight**: root `test-extraction.js` + the broken `test:root` script,
   `DrawingPlate.jsx`, `SummaryBar.jsx`, `FilterBar.jsx`, `inspect-pdf.js` (its verdict logic
   is preserved in the hybrid spec), `EXTRACTION_RESPONSE_SCHEMA`.
4. **Capture `a.id` and populate `drawing_reference` in the parse lane**
   (`parse-extraction-service.js:44-50`) — two small additions that unlock both feasibility
   items (AutoLISP linking and write-back) and improve `/ask` retrieval for parse projects.
5. **Bound the 429 retry** in `extraction-service.js:150-155` with an attempt counter — the
   current recursion is an unbounded loop waiting for a rate-limit storm.
