# Eval case conventions

This doc defines the naming and metadata conventions for cases in the eval harness. The eval runner resolves labels by filename (PDF in `pdfs/` → label at `labels/<same-stem>.json`), so the filename is load-bearing.

## Filename scheme

| Pattern | Meaning | Tracked in git? |
|---|---|---|
| `case_NNN_<slug>` | Working-set case, sequential ID | Yes |
| `case_hNN_<slug>` | Holdout case (excluded by `--working-set`) | Yes |
| `case_C<NN>_<slug>` | Collaborator-proprietary case, working set | **No** (gitignored) |
| `case_hC<NN>_<slug>` | Collaborator-proprietary case, holdout | **No** (gitignored) |

The `case_C*` prefix is the *policy hook*: anything matching it is `.gitignore`d so client-confidential material stays local. There is no realism information in the filename — see metadata below.

> Historical note: an earlier convention used `case_R*` and `case_HR*` as a one-bit "real vs synthetic" flag. That conflated substrate-realism with markup-realism (see below) and was retired when case_R001 was renamed to case_011. Anything currently called `case_R*` predates this convention.

## Metadata: substrate × markup

Each label JSON carries two independent realism fields:

```json
"substrate_source": "synthetic" | "real_self" | "real_public" | "real_collaborator",
"markup_source":    "synthetic" | "self_authored" | "real_reviewer"
```

**`substrate_source`** — where the underlying plan PDF came from:
- `synthetic` — generated by a script in `evals/synthetic/<sheet>/generate.py`
- `real_self` — a real production drawing the user owns or produced
- `real_public` — a real production drawing pulled from a public permit record (e.g. municipal portal)
- `real_collaborator` — a real production drawing shared by a third party, may carry confidentiality expectations (these are the cases that get `case_C*` filenames and stay out of git)

**`markup_source`** — who/what authored the redlines:
- `synthetic` — drawn programmatically (e.g. the synthetic generators) or scripted from a Claude draft with no human review pass
- `self_authored` — the user added the redlines by hand in PDF-XChange or similar, possibly from a Claude-suggested list
- `real_reviewer` — actual reviewer comments from a real project review cycle

## Why two fields, not one

The two dimensions test different things:

- **Substrate realism** stresses the *vision pipeline*: dense sheets, real abbreviations, real symbol density, scale, line weight, scanned vs vector PDFs.
- **Markup realism** stresses the *extraction prompt*: how a real engineer phrases a comment vs how a synthetic generator phrases one. Real reviewers are terse, idiomatic, and often ambiguous in ways the prompt has to learn to flag.

A `real_public + self_authored` case (e.g. case_011) isolates substrate complexity. A `real_public + real_reviewer` case (e.g. case_006) is the ceiling test — both axes maxed.

When scoring, you can slice the run JSON by either field to see which axis a regression is on.

## Authoring `self_authored` markups

When you hand-draw redlines on a real substrate (PDF-XChange or similar), follow these rules so the case is valid:

1. **Author the label JSON first, then mark up to it.** Ground truth is written before the PDF is touched — no post-hoc labeling, no ambiguity about the expected answer.
2. **Every markup must be uniform red** — clouds, callouts, leaders, and text. Black callout text blends into the base drawing and the vision model reads it as substrate, not markup, which silently undercounts what the pipeline can detect. (Discovered on case_011, which had mixed red/black callouts; recoloring changed its behavior and its pre-fix runs were disregarded.)
3. **Comments must be drawn on the page** as text boxes/callouts, not typed into the editor's comments sidebar — the sidebar lives in PDF metadata and never reaches the rasterized image the pipeline sees.
4. **Flattening is optional — skip it.** pdf2pic/ghostscript renders live annotation appearance streams (see `src/utils/pdf-converter.js`, which passes no `-dShowAnnots=false`), confirmed on case_011. Flattening would only future-proof against render-path changes, and **free PDF-XChange gates Flatten behind a license — using it stamps "DEMO" watermarks on every page**, which corrupts the substrate. So for this toolchain: save the marked-up PDF un-flattened straight to `evals/pdfs/`. Keep the editable copy in `dogfood/sources/` anyway.
5. **Seed 1-2 deliberately ambiguous marks** per sheet (`is_ambiguous: true`, `specificity_target: 0`) — a commentless cloud, a bare `?` — to measure the orphaned-cloud / hallucinated-comment failure mode.
